# Release note: the from-scratch rebuild

What has to happen around the deploy of the `rebuild` branch, in order. Everything below is
the release engineer's checklist, not a description of the code. The acceptance run
(blueprint section 13) has to be green before any of it starts.

## 1. Deploy after 00:00 Europe/Berlin

The edition rolls over at midnight Berlin time (`src/server/edition.ts`, `src/lib/daily-seed.ts`).
Deploying inside a live day swaps the board generator under people who are mid-run on the
old build: their next submit would be validated against a board they never saw. Ship right
after the rollover, so the first daily of the new build is generated by the new build.

## 2. Before the deploy: the database

Run these against production in this order. The URL comes from `.env.local`
(`NEXT_PUBLIC_SUPABASE_URL`), the key from the service-role key file:

```
export SUPABASE_SERVICE_ROLE_KEY_FILE=~/.config/countrivo-seo/supabase-service-role.key
```

A shell on this machine still exports an older project's `SUPABASE_URL` and
`SUPABASE_SERVICE_ROLE_KEY`. `scripts/check-daily-ranks.ts` compares the key's project ref
with the URL and refuses to run when they disagree; do the same by eye for any ad-hoc curl.

**2.1 The slug rename must be applied.**
`supabase/migrations/20260829120000_rename_country_draft_to_blind_pick.sql` moves every run,
stat row, daily puzzle and challenge of the eight-stat game from `country-draft` to
`blind-pick`, so the history follows the game rather than the URL. It is safe to re-run.
Verify: `game_runs?game_slug=eq.country-draft` is empty before the new cabinet draft ships
its first run.

**2.2 Delete the playtest accounts.**
Every script that plays a signed-in flow joins as an anonymous guest named `playtest...`.
Delete exactly those accounts through the admin API
(`DELETE /auth/v1/admin/users/{id}`, filtered on `is_anonymous` and a `display_name`
starting with `playtest`). Never delete by age: real guests share the database.

**2.3 Re-run `compute_daily_rankings` for every slug a playtest touched.**

```
npm run check:ranks              # report every daily board
npm run check:ranks -- --fix     # recompute the boards that drifted
```

Why this step exists: `game_runs.rank_daily` and `percentile` are written once, at submit
time, by the `compute_daily_rankings` RPC (`src/app/actions/game-runs.ts`). Deleting a
playtest user removes their runs but never re-runs the RPC, so every surviving row of that
day keeps the rank it earned against runs that no longer exist. The leaderboard prints the
stored rank while the home board computes the position from the ordered rows, so the two
pages then disagree about the same run.

Seen for real on 29 August 2026: run 953 (blind-pick, 29 Aug) stored `rank_daily = 5` and
`percentile = 20` after 2.2 deleted the other four rows of that day, and
`/games/blind-pick/leaderboard` printed `5` under a header reading `1 shot`. Repaired with
`npm run check:ranks -- --slug blind-pick --date 2026-08-29 --fix`; all 104 daily boards
now agree.

`--force` recomputes even the boards that look fine; `--slug` and `--date` narrow the run.

## 3. The deploy

Push the merged branch to `main` (Vercel is git-linked and builds production) or run
`~/.config/countrivo-seo/deploy.py --prod`. Never the file-upload path twice in a day
(5000 files per day). Restart any local `next start` after a build before testing it: a
stale server serves old chunks and every page falls into the error boundary.

## 4. What is not carried over

**Old localStorage progress is not read.** The new play frame keeps an unfinished daily in
the `cv_p_{slug}` cookie and the finished set in `cv_done`, both written server-side, so the
first HTML already carries the resumed board. The keys the old build wrote under
`countrivo_...` are ignored; nothing migrates them and nothing needs to. The only localStorage
this build touches is `countrivo_sound_muted`, `countrivo_push_prompt_seen` and the
write-only lockout belt in `src/lib/storage.ts` (kept so a rollback still finds its
lockouts). A player who is mid-run at the cutover starts that board again; a player who has
already finished today stays finished, because the lockout comes from the cookie and, when
signed in, from the stored run.

**The roster changes URL meaning.** `/games/country-draft` now serves the cabinet draft;
the eight-stat game is `Blind Pick` at `/games/blind-pick`. `/games/world-draft` and the
eleven cut games redirect permanently (`next.config.ts`). Anyone holding a bookmark to a cut
game lands on the closest surviving page, not a 404.

## 5. After the deploy

- `npm run check:ranks` once more (the deploy itself writes no ranks, but the first live
  submits do; this confirms the RPC is reachable in production).
- `npm run check:crawlers` against the production host: every floor still passes.
- Spot-check by hand: `/games/country-draft` (cabinet draft, seats), `/games/blind-pick`
  (eight stats), `/games/blind-pick/leaderboard` (the printed rank matches the row's
  position and the `shots` count in the header), `/games/world-draft` returns 301.
- Submit one real daily from a phone and confirm the run appears on the home board and on
  the leaderboard with the same position on both.

## 6. Rollback

Promote the previous Vercel deployment. The database is not rolled back: the slug rename in
2.1 is data, and reverting it would strand every run submitted under `blind-pick` after the
deploy. Decide before running 2.1, not after.
